# Inventario de firmware MKGW3 y conexión B5 asíncrona

La fuente de protocolo es `documentación/guia-referencia-mqtt-mkgw3.pdf` (septiembre de 2026, páginas 2–5 y 7). La guía reserva `1063` y `1066` a MKGW3 V2.X.X. También señala las opciones V2 `1041.relation=8` y `1060.phy_filter=4`. La estructura JSON de respuesta a `2201` no está definida con precisión suficiente para implementar un parser seguro.

## Versión y capacidades

La migración aditiva `backend/migrations/007_gateway_model_firmware_connection.sql` añade a `gateways` `product_model`, `firmware_version`, `firmware_evidence` y `firmware_recorded_at`. Las filas existentes quedan con valores `NULL`: ninguna se declara V2 por defecto. Un técnico autorizado y limitado por empresa puede registrar `MKGW3`, una versión explícita y una referencia comprobable mediante `PUT /api/gateways/:id/firmware`; puede revocarla con `DELETE /api/gateways/:id/firmware` para volver al estado desconocido. La referencia debe tener forma `inspection:<referencia>` o `device-info-2002:<referencia>`; el operador conserva la evidencia fuera del campo. La actualización/revocación y su auditoría técnica se confirman en la misma transacción. Esta anotación es manual, no una detección automática ni una prueba criptográfica de la versión. No se envía `2002` ni ningún otro comando durante el desarrollo o las pruebas.

Con modelo, versión o evidencia ausentes o inválidos, la API rechaza con `409` `1063`, `1066`, `1041.relation=8`, `1060.phy_filter=4` y la configuración B5 de cuatro pasos (incluye `1063`), tanto en la ruta pública como en la interna. La UI deshabilita esas opciones, pero el bloqueo decisivo está en Backend. Los comandos compatibles sin requisito V2 siguen disponibles con sus validaciones y permisos habituales.

### Inventario y puesta en marcha de gateways existentes

Antes de activar esta versión en un entorno operativo, exportar una lista de `gateways` activas (ID, MAC, empresa y ubicación), cotejarla con el inventario físico y registrar para cada unidad el modelo, versión de firmware y referencia a evidencia conservada por operaciones (etiqueta/acta de inspección o lectura `2002` ya existente). La migración **no** completa estos datos: después de aplicarla todas las unidades existentes quedan en estado desconocido. No copiar la versión de otra gateway, no inferirla por MAC y no enviar `2002` ni otros comandos durante la preparación. Un técnico registra cada resultado mediante `PUT /api/gateways/:id/firmware` y comprueba el listado y la auditoría por empresa; si la evidencia es dudosa, deja la versión sin registrar. Validar en staging que los cuatro pasos B5 y las opciones V2 están habilitados solamente en las unidades documentadas, y que las demás conservan presencia, alarmas lógicas y comandos compatibles. Planificar la ventana de cambio con operaciones: si la configuración B5 de una gateway existente es imprescindible y todavía no hay evidencia, **no desplegar** esta versión hasta completar el inventario o acordar otra vía segura. Revocar con `DELETE /api/gateways/:id/firmware` ante una corrección del inventario; esto vuelve a bloquear las opciones V2 sin borrar historial. No modificar filas a mano ni rellenar versiones por defecto.

## Conexión B5

`1150` con `result_code=0` significa que la gateway aceptó la petición; **no** significa conexión BLE establecida. El ejecutor espera `3151`, pero el informe no incluye un identificador inequívoco del intento. Incluso con MAC del tag y orden local posterior al ACK, podría corresponder a una solicitud anterior. Un `3151` sin MAC, con MAC distinta o tardío tampoco establece la conexión. La migración `008_b5_connection_unverified.sql` añade `connection_state='unverified'` al diario, sin modificar filas históricas. La API devuelve `202 connection_unverified` para aceptación sin conexión atribuible, informe incierto o timeout de confirmación. Horneo registra `attempted_unverified`, no envía LED/buzzer/vibración, no repite `1150`, no prueba otra gateway y no envía `1200` como efecto colateral de ese intento. La alerta lógica y su auditoría durable se mantienen. `B5_CONNECT_TIMEOUT_MS` se limita a 15 s para quedar dentro de los 20 s del cliente Horneo.

El `202` por ACK histórico ambiguo sigue indicando incertidumbre, y no habilita acciones físicas cuando la conexión está sin verificar. Un `3151` no actualiza directamente el ACK genérico de `1150`. El parser `2201` queda **bloqueado**: falta el contrato JSON exacto de `ble_conn_list` y de la respuesta con MAC/tipo. Para rehabilitar la alarma física automática tras `1150` se necesita una respuesta documentada que permita verificar el tag conectado y atribuir la conexión al intento, o un mecanismo contractual equivalente del fabricante. Hasta entonces esta rama no debe considerarse lista para despliegue si se exige el disparo físico B5 automático. No se inventan campos ni se contacta hardware real en los tests.
